

IMPORTANT:
This is NOT a serverless application. The backend must run as a persistent Node.js process

==================================================
1. TECHNOLOGY STACK
==================================================

Frontend:
- React.js
- Vite
- HTML5 Canvas
- CSS
- Socket.IO client

Backend:
- Node.js
- Express.js
- Socket.IO
- JavaScript
- In-memory server-side room/game state

Game logic:
- Implement as separate backend modules/services.
- Do NOT put all game logic directly inside Express route handlers.
- Express is responsible for HTTP/API functionality.
- Socket.IO is responsible for real-time multiplayer communication.
- The server must be authoritative for all game state, scores, turns, timers, secret words, and guesses.

Room management:
- Server-side room management.
- Rooms should exist in backend memory.
- Each room should have a unique room code.
- Players join rooms using the room code.
- A player can only belong to one active room at a time.

Deployment:
Frontend → Vercel
Backend → Render
Backend must be a persistent Web Service on Render.
DO NOT use Vercel serverless functions.
DO NOT use Render static hosting for the backend.
DO NOT introduce AWS Lambda, Firebase Functions, Supabase Edge Functions, etc.

==================================================
3. GAME CONCEPT
==================================================

Implement the following game flow:

1. User opens the frontend.
2. User can:
   - Create a room
   - Join an existing room
3. Creating a room generates a short unique room code.
4. User enters a nickname.
5. Players join the room.
6. Lobby displays all connected players.
7. Host can start the game.
8. Server selects the first drawer.
9. Drawer receives 3 word choices.
10. Drawer chooses one word.
11. Other players must NOT receive the secret word.
12. Drawing round starts.
13. Drawer draws on the canvas.
14. Drawing events are sent through Socket.IO.
15. Server broadcasts drawing events to the other players in the room.
16. Other players submit guesses.
17. Server validates guesses.
18. Correct guessers receive points.
19. Faster correct guesses should receive more points.
20. Drawer receives points based on how many players successfully guess.
21. Round ends when:
   - Timer reaches zero, OR
   - Everyone except the drawer has correctly guessed.
22. Reveal the word.
23. Display round scores.
24. Next player becomes drawer.
25. Continue for configurable number of rounds.
26. Display final scoreboard.
27. Allow players to play again or return to lobby.

==================================================
4. SERVER AUTHORITATIVE ARCHITECTURE
==================================================

The server must be authoritative.

Never trust the frontend for:

- Scores
- Secret word
- Current drawer
- Round number
- Timer
- Guess correctness
- Game status
- Player permissions

The client should only send intentions/actions.

For example:

BAD:
client sends:
{
  score: 500
}

GOOD:
client sends:
{
  type: "submit_guess",
  guess: "apple"
}

Then the server determines the result.

7. DRAWING SYSTEM
==================================================

Use HTML5 Canvas.

Implement:

- Pencil
- Eraser
- Brush size
- Color picker
- Clear canvas
- Undo
- Redo if practical

Do NOT send canvas screenshots/images continuously.

Transmit drawing operations/strokes through Socket.IO.

A drawing operation should contain enough information to reproduce the stroke, for example:

{
  type: "stroke",
  points: [...],
  color: "#000000",
  width: 5,
  tool: "brush"
}

Optimize network usage.

Do not emit an event for every raw mousemove without throttling/batching.

The server should validate that only the current drawer can submit drawing operations.

When a new player joins an active game, provide the necessary current drawing state so they can synchronize with the existing canvas.

12. BRUTALIST / BRUTALISM UI
==================================================

The entire application must use a strong modern brutalist visual language.

DO NOT create a generic SaaS dashboard.
DO NOT use glassmorphism.
DO NOT use soft gradients.
DO NOT use excessive rounded cards.
DO NOT use the typical modern AI-app aesthetic.

Use:

- Heavy black borders
- Thick 3px–5px borders
- Hard rectangular panels
- Sharp corners or very small border radius
- Large bold typography
- High contrast
- Solid blocks of color
- Offset shadows
- Raw, playful visual hierarchy
- Large buttons
- Chunky controls
- Strong hover states
- Slightly chaotic but intentional layout
- Monospace or bold display typography where appropriate

Suggested visual direction:

Background:
off-white / warm cream

Primary:
black

Accent colors:
bright yellow
electric blue
hot pink
lime green
orange

Use black text on bright accent blocks.

Buttons should feel physical.

Example:

button {
  border: 4px solid #000;
  box-shadow: 6px 6px 0 #000;
}

On hover:
- translate slightly
- reduce shadow

On active:
- move into the shadow

Cards/panels should use hard shadows rather than blur.

The game should feel like a physical board game mixed with an internet drawing game.
